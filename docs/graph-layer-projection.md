# Read-only graph-layer projection

`apps/api/src/graph-projection.ts` defines a deterministic, read-only graph
projection model for the API and MCP read transports. It is deliberately additive:
the canonical card, microstructure, mathematical-view, analogy, and typed
composition documents remain the sources of truth.

## DEC-0002 contract

The projection keeps these dimensions separate:

- `system`: a reviewed architecture card;
- `property`: a property/feature declared by one system;
- `mathematical-contract`: a mathematical view and its question/assumptions;
- `microstructure`: a scale-aware architectural unit;
- `analogy`: a bounded cross-domain structural comparison;
- `composition`: a typed composition candidate;
- `component` and `property-effect`: records inside that composition candidate.
- `relation`: an explicitly declared typed adapter or boundary record.

Explicit Architecture Card `relations` are also projected as directed edges
between `system:<source>` and `system:<target>` nodes. Their `type`, claim
fields, evidence IDs, notes, and declared validity scope are copied without
normalization into another relation or inferred from card names, categories,
similarity, or layout. Unknown endpoints are omitted. The legacy
`related_systems` navigation field is not used by this layered projection.

The projection does **not** turn navigation categories into graph nodes. The
existing model-family groups are UI-only. A client may show `Others` only as
an explicit fallback for an item with no UI mapping; it must never serialize
`Others` as a canonical graph relation or infer an edge from a category/name.
No feature-to-feature relation is generated by this module.

## Evidence and uncertainty

Every emitted source-backed node/edge carries `claim_type`, `claim_status`,
and `evidence_ids` when present. Validity scope is retained, including
deployment origins. Typed composition candidates retain `proven: false`,
discovery method/provenance, source and target communities, cross-community
`path`, uncertainties, disagreements, counterexamples, and non-equivalence
metadata. Invalid or dangling typed endpoints are omitted; the projection does
not repair them or upgrade a claim.

## Query and UX guidance

Use independent layer toggles and one-hop expansion from a selected system.
Render layer and claim status distinctly, then show evidence, scope,
uncertainty, and candidate provenance in a detail panel. Force-layout position,
proximity, direction, or depth must not be presented as similarity, chronology,
causation, influence, or proof. Navigation facets should remain separate from
the graph payload.

`GET /api/graph/layers` and the MCP `get_layered_graph` tool accept an optional
`origin` filter. Documents
with no declared deployment origin remain visible; scoped documents are shown
only when the requested origin is listed. This is a filter, not a relation.

Both API and MCP projections read only reviewed `data/systems` and D1 rows.
They never read or seed `data/drafts`; the projection has no write or
promotion operation.

## Performance guidance

For `N` systems, `F` properties, `V` views, `C` typed composition records, and
`D` standalone documents, projection costs `O(N + F + V + C + D)` before
deterministic sorting, and uses `O(K)` space for `K` emitted nodes and edges.
Small catalogues can be fetched once and filtered client-side by layer. Larger
catalogues should cache by origin and use stable-ID indexes plus bounded
neighborhood expansion rather than rendering all metadata at once.
